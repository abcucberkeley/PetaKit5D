# 0002: FFTs identical to MATLAB's, without MATLAB

Status: accepted for Linux x86-64 (exact); macOS ARM and Windows to be measured against Linux.

## Context

Deconvolution, OTFs, PSF resampling, the back projector and 3D registration run on MATLAB's
`fft`, `ifft`, `fftn` and `ifftn`. MATLAB R2024b computes them with FFTW 3.3.8
(`libmwfftw3f` / `libmwfftw3`, version string `fftw-3.3.8-sse2-avx`) through a driver of its own.
Whether a port can give MATLAB's bits at all depended on two unknowns: whether a stock FFTW build
makes MATLAB's plans and bits, and what MATLAB's driver does exactly.

## Findings

**MATLAB's library is stock FFTW 3.3.8.** Built by MathWorks with GCC 10.3.0 at `-O2`
(`fftw_cc`), `--enable-sse2 --enable-avx`, threads combined. Its 603 codelets (227 scalar, 188
SSE2, 188 AVX) are those of a stock build with the same options; the only addition is an
assertion hook (`fftw[f]_set_assertion_failed_fcn`). Loaded outside MATLAB (it needs only libc,
libm, libpthread), it makes the same plans as inside MATLAB (414 of 414 plans logged in two MATLAB
sessions), whatever was planned before and at any buffer offset that is a multiple of 16 bytes
(FFTW looks at alignment modulo 16 with SSE2/AVX).

**Stock 3.3.8 and 3.3.10 both equal it, plan for plan and bit for bit**: every n in 1..4096
and 13 larger lengths, r2c, c2c forward and backward, c2r, 1 and 4 lines per execute, single and
double, 3 input patterns: 65,728 cases, 0 plans and 0 outputs differ (GCC 13.2, `-O2`). Between
3.3.8 and 3.3.10 the planner, solvers and API are unchanged and the 432 generated codelets have
the same statements (only their order differs); the one rule that changed (`SIMD_VSTRIDE_OKA` for
double-precision SSE2) never applies to interleaved complex data.

**MATLAB's driver** (found with an `LD_PRELOAD` shim that logged every plan and execute, then
confirmed bit for bit):

- Plans: rank 1, `FFTW_ESTIMATE`, FFTW threads 1, out of place, contiguous lines in scratch; one
  plan for 4 lines per execute and one for a single line. Strided lines are gathered.
- Real input: r2c along the first transformed dimension, each line filled to full length by
  conjugation (the imaginary part negated), c2c along the others. `fftn` then makes the result
  exactly Hermitian: an element whose mirror has the lower linear index becomes the mirror's
  conjugate, its imaginary part computed as 0 - im (a zero becomes +0, unlike the negation of the
  line fill); self-conjugate elements get imaginary part 0. Complex input: c2c.
- Inverse: if the input is conjugate symmetric (exact IEEE test of every element: per line for
  `ifft`, N-D for `ifftn`; -0 counts as 0, NaN fails, one failing line makes every line c2c) or
  `'symmetric'` is given, c2c along every transformed dimension but MATLAB's last one and c2r
  along that; else c2c. MATLAB's last dimension is the last of its size (2 dimensions at least),
  so for a column vector it is the second, of length 1: c2c along the first, then the real part.
  `ifftn(..., 'symmetric')` first applies `fftn`'s fill to the (padded) data; `ifft(...,
  'symmetric')` does not. `'nonsymmetric'` is the default (auto-detect), not a forced c2c.
- Every inverse stage divides by its length. A complex result whose imaginary parts are all zero
  is returned as real. `n` and `siz` pad or truncate before the transforms (every line of the
  padded array is transformed). A transform along a length-1 dimension without `n` returns the
  input; a 1x1 input counts as a row; integer and logical input become double. `siz` needs at
  least `ndims(X)` elements (2 at least, also for vectors and scalars); an empty `siz` is the
  input's size; `n` and `siz` must be non-negative integers.
- Lines MATLAB runs alone: when MATLAB runs its FFTs in parallel and n * N * (bits of n) > 98304
  (n the transform length, N the lines of the stage) it halves the lines until pieces have at most
  32; each piece runs groups of four from its start and its last (length % 4) lines alone; along a
  dimension d > 1 groups also restart every prod(size(1:d-1)) lines. A session whose first FFT ran
  on one thread never splits. The lanes of a group are independent (checked for every n up to
  4096, both libraries), so only which lines run alone matters.

## Decision

- **FFTW 3.3.8**, MATLAB R2024b's own release, built by our CMake from the release tarball (fetched
  by URL and SHA-256, `python/cpp/fft/fftw.cmake`), single and double precision, static, symbols
  hidden inside the extension, `-ffp-contract=off`, with FFTW's own source lists and MATLAB's
  codelet sets: SSE2 and AVX (no FMA, no AVX2/AVX-512), SIMD flags only on the SIMD codelets as
  FFTW's configure does (FFTW picks them at run time from the CPU), no FFTW threads, no Fortran
  wrappers. Our build has exactly MATLAB's 603 codelets per precision. `PK5D_FFTW_VERSION=3.3.10`
  builds the newest release, which gives the same plans and bits but is not faster (two
  interleaved comparisons on c24 nodes, 7 and 11 repeats: 3.3.10/3.3.8 = 0.99 and 1.01 at 24
  threads, 1.03 and 0.98 at 4, 1.00 and 1.01 at 1). The user's rule was the newer release if it
  is newer, faster and identical; it is not faster. 3.3.8 is also MATLAB's own code on every CPU,
  while 3.3.10's changed SSE2 rule for double precision was not tested on a CPU without AVX.
- **The driver** (`python/cpp/fft/driver.cpp`) reproduces MATLAB's rules above with MATLAB's plans.
  Our threads take any lines; each line is computed as MATLAB computes it (in a group or alone),
  so results never depend on our thread count. Only the parts MATLAB's result depends on are
  computed (the inverse transforms only the half the c2r stage reads; the forward writes only the
  half the Hermitian fill does not overwrite).
- **Modes:** the default is MATLAB's parallel mode (production MATLAB runs with several
  threads); `matlab_parallel=False` gives the results of a MATLAB session that started on one
  thread.
- **Test-only switch:** `PETAKIT5D_TEST_FFTW` (MATLAB's `bin/glnxa64` folder, or the two library
  paths) runs the same driver on MATLAB's own FFTW, to tell port errors from library differences.
- **Other targets** can link `pk5d_fftw` (FFTW) and `pk5d_fft_driver` (the driver) with
  `pk5d_add_extension(... LIBRARIES ...)`.

## Results (Linux x86-64, MATLAB R2024b Update 5)

Bit-identical cases (class, size and every bit, signed zeros included), MATLAB in its parallel
mode (24 computational threads; the 1D pack 8) and in its single-thread mode, and our driver on
MATLAB's own FFTW:

| Pack | Cases | Parallel mode | Single-thread mode | On MATLAB's FFTW (parallel mode) |
|---|---|---|---|---|
| 1D lengths 2..1024 (n x 7: groups and lines alone), every kind, both precisions | 8,768 | 8,768 | 8,768 | 8,768 |
| MATLAB's rules (real results, symmetry test, padding, `siz`, `'symmetric'`, vectors, split threshold, signed zeros, the fill's zeros, integers) | 779 | 779 | 779 | 779 |
| 3D sizes of the demos, the decon tests and a real decon batch (up to 3082 x 11530 x 4 and 1800 x 512 x 500) | 130 | 130 | 130 | 130 |
| Argument rules (errors, empty and scalar inputs, `n` and `siz`) | 40 | 40 | | |

FFTW 3.3.10 gives the same: the library comparison above, and the 1D, rules and 3D packs run with
it. The 1D and rules packs are in the tests as digests of MATLAB's outputs (both modes).

## Not exact by construction, or not checked

- **macOS ARM:** FFTW has no SSE2/AVX there (we build the scalar codelets, no NEON): other plans
  and other last bits than on Linux. To be measured against Linux (open).
- **Windows x86-64:** the same codelets, compiled by MSVC (`/arch:AVX`, `/fp:precise`, no fused
  multiply-adds): expected to equal Linux; not run yet (open). MATLAB's own Windows and macOS
  libraries were not examined.
- A CPU without AVX gets other plans (FFTW's run-time choice), as MATLAB on such a CPU would; the
  digest tests skip there.
- Not ported: `fft2`, `ifft2` and the GPU transforms.
