# 0003: GPU support (CuPy, run-time compiled kernels, cuFFT plans, device choice)

Status: proposed (task F09), 2026-11-11; the plans on the (z, y, x) layout (task F19),
2026-11-12. Measured on NVIDIA Titan V and V100 (compute capability 7.0, driver 580.173), A100
(8.0, driver 580.95) and B200 (10.0, driver 595.91), Python 3.12, Linux x86-64.

## Context

PetaKit5D runs its deconvolution (and optionally deskew/rotate) on NVIDIA GPUs: MATLAB gpuArray
code and two CUDA mex files. The Python port must run on every GPU generation users have, from
Volta (7.0) to Blackwell (10.0) and on GPUs newer than the CUDA release it was installed with,
without a CUDA toolkit to build, and without a GPU at all for every CPU path. GPUs on shared
clusters are not always isolated between jobs, so a process must not assume a GPU is free.

## Decisions

### 1. The environment: CuPy for CUDA 12 and CUDA 12.9 component wheels

```
cupy-cuda12x==14.2.0  nvidia-cuda-runtime-cu12==12.9.79  nvidia-cuda-nvrtc-cu12==12.9.86
nvidia-cufft-cu12==11.0.8.103  (proposed; or 11.4.1.4, see below)  cuda-pathfinder==1.8.6
```

All from PyPI, nothing from a system toolkit (CuPy finds the wheels' libraries with
cuda-pathfinder). Optional: the package installs and runs without them (extra `gpu`).

- **cuFFT 11.0.8.103, the version MATLAB R2024b bundles, is proposed** (the user decides): with it
  our FFTs are MATLAB's bit for bit on Titan V, A100 and B200 (measurements below), at the same
  speed as cuFFT 11.4.1.4 (CUDA 12.9's) on all three. On a B200 the driver compiles its kernels
  from PTX, as for MATLAB with forward compatibility: about 0.2 s more on the first use of a size,
  then cached by the driver. 11.4.1.4 is the alternative if native Blackwell kernels matter more
  than MATLAB's bits.

- **CUDA 12.9 is the only line that serves every GPU in use.** NVRTC 12.9 compiles for 5.0 to
  12.1 (Volta and Blackwell included). CUDA 13 (NVRTC 13.5) no longer compiles for 7.0: a Titan V
  or V100 is refused ("older than the oldest GPU this CUDA compiler supports (7.5)", measured).
  NVRTC 12.0 to 12.7 don't know Blackwell (12.2 stops at 9.0).
- **Prefer cubins.** The driver runs cubins of a newer CUDA minor release (minor version
  compatibility), but compiles PTX only from an NVRTC no newer than itself: PTX from NVRTC 13.5
  (PTX ISA 9.5) fails on a 595 driver (CUDA 13.2) with "the driver (CUDA 13.2) cannot compile PTX
  from NVRTC 13.5" (measured on B200).
- Not needed: cuBLAS, cuSOLVER, cuSPARSE, cuRAND (CuPy's `[ctk]` extra pulls them: 2 GB instead
  of 1 GB). An install takes 13 to 17 s from the wheels, no compilation.

### 2. Kernels: our own NVRTC driver and cache (`petakit5d.gpu.kernels`)

`.cu` sources (`cpp/cuda/<group>/`) are compiled at run time with NVRTC through CuPy's NVRTC
binding and loaded with `cupy.cuda.Module`.

- **Target**: the GPU's own architecture as a cubin when NVRTC knows it; else PTX for the newest
  architecture NVRTC knows below the GPU's, which the driver compiles (cuLink) into a cubin that
  is cached too. No reliance on the driver's JIT cache for our kernels.
- **Options**: `--std=c++17 --fmad=false`; no `-ftz`. As `-ffp-contract=off` for the C++ kernels:
  no fused multiply-adds, subnormals kept.
- **Cache**: one file per compiled module in `PETAKIT5D_CACHE_DIR/cuda-kernels` (default: the
  user's cache folder), named by the SHA-256 of source, headers next to it, options and NVRTC
  version (driver version and compute capability too for driver-compiled cubins), written under
  a temporary name and renamed: parallel jobs share it safely; a damaged file (checksum) is
  compiled again; an unwritable folder warns once and compiles per process.
- **Not CuPy's `RawModule`**, for three reasons measured with CuPy 14.2: it adds `-ftz=true`
  (flushes subnormals: `x * 1` of 1e-40 gives 0) and keeps NVRTC's `--fmad=true`; with an NVRTC
  that doesn't know the GPU it compiles a cubin for the newest architecture NVRTC knows
  (`sm_90` on a B200 with NVRTC 12.2), which the GPU can't run; its cache is keyed by CuPy's own
  choices.
- **CuPy's own kernels** (element-wise operations, reductions) have that last problem too: when
  the selected GPU is newer than NVRTC knows, `select_device` switches CuPy to PTX
  (`cupy.cuda.compiler._use_ptx`, the setting behind `CUPY_COMPILE_WITH_PTX`), so the driver
  compiles them. Measured on a B200 with NVRTC 12.2: without it `cupy.arange(4) * 2` fails with
  `CUDA_ERROR_NO_BINARY_FOR_GPU` (CuPy picks `-arch=sm_90`, a cubin); with it, it runs.
- Testing switch: `PETAKIT5D_GPU_TARGET=ptx` (PTX for the driver even when NVRTC knows the GPU)
  or `=<arch>` (act as if NVRTC knew nothing above it).

### 3. cuFFT: our own plans, one work area (`petakit5d.gpu.fft`)

Volumes are (z, y, x) C arrays (the port's convention); MATLAB's (y, x, z) Fortran volume has
the bytes of the C array (z, x, y), `core.arrays.matlab_order(vol)`.

- `RealFFTPlan`: single precision real-to-complex (R2C) and complex-to-real (C2R) plans of a C
  array, made as the GPU decon mex makes its plans: cuFFT's row-major dimensions of the shape,
  size-1 dimensions other than the last left out, the half spectrum along the last axis (x of a
  volume, `(nz, ny, nx // 2 + 1)`), `cufftMakePlanMany` with automatic allocation off, and **one
  work area for both plans**, the larger of the two, taken from CuPy's memory pool. R04's half
  spectra option.
- `ComplexFFTPlan`: the complex-to-complex (C2C) plan of the same dimensions.
- `MatlabFFTPlan`: C2C of (z, y, x) volumes **with the bits of MATLAB's gpuArray `fftn` and
  `ifftn`**, R04's default (the full spectra MATLAB's GPU code uses). MATLAB's plan follows its
  layout, cuFFT's row-major `(nz, nx, ny)`; no cuFFT plan over (z, y, x) memory can express it
  (cuFFT's advanced layout nests each dimension's stride in the next one's), and the bits depend
  on the plan (the native plan's differ in 80-95% of values, see the measurements). So the plan
  is MATLAB's, `ComplexFFTPlan(matlab_shape(shape))`, and its spectra stay in MATLAB's layout,
  C arrays (kz, kx, ky): `forward` transposes each z plane of a float32 or complex64 volume into
  the spectrum's array (32 x 32 tiles in shared memory, fused with the conversion to complex a
  transform of real data needs anyway) and transforms in place; `inverse` transforms in place
  and transposes back, dividing each part by N as `ifftn` does (in double, rounded to single),
  into a complex64 volume or its real part (float32). Products of spectra (an OTF with a
  transform) need no transposes, and `to_native`/`from_native` give (kz, ky, kx) to a step that
  needs it. No extra pass or buffer, and the work area of the same plan.
- A plan in MATLAB's layout, for the tests that prove equality with MATLAB's GPU results (and
  the mex's half OTF): `RealFFTPlan` or `ComplexFFTPlan` of `matlab_shape(shape)`, (nz, nx, ny),
  on `np.ascontiguousarray(matlab_order(vol))`: the mex's plans, their half spectrum along y.
- cuFFT is called through ctypes on the very library CuPy loaded (cuda-pathfinder), because
  CuPy's plans allocate a work area each and CuPy exposes no `cufftSetWorkArea`. The GIL is
  released during the calls. `PETAKIT5D_CUFFT_LIBRARY` selects another libcufft (testing).
- A plan cache keeps the last 2 plans (a job's files usually share a size); a plan dropped from
  the cache is destroyed when no caller holds it. Plans run on CuPy's current stream.
- Out of GPU memory in planning raises `CuFFTMemoryError` (a `MemoryError`), as the mex maps
  `CUFFT_ALLOC_FAILED` and `CUFFT_INTERNAL_ERROR` in planning to MATLAB's out-of-memory errors.

### 4. Device choice (`petakit5d.gpu.device`)

- The GPUs are those CUDA lists (`CUDA_VISIBLE_DEVICES`, set by Slurm for a job's GPUs).
- **New rule, unlike MATLAB**: a process in a Slurm job without GPUs of its own
  (`SLURM_JOB_GPUS`, `SLURM_STEP_GPUS` and `SLURM_GPUS_ON_NODE` unset) and without
  `CUDA_VISIBLE_DEVICES` uses no GPU, with the reason: on nodes that don't hide their GPUs, the
  GPUs it sees belong to other jobs (MATLAB would take GPU 0 there). Setting
  `CUDA_VISIBLE_DEVICES` uses them anyway.
- Usable: NVRTC compiles for the GPU and it is not in prohibited compute mode. MATLAB's forward
  compatibility (needed for B200 in R2024b) has no counterpart: PTX covers newer GPUs.
- `select_device(index=None, need_bytes=0)` creates the context and checks free memory (our
  pool's cached blocks count as free); a GPU that fails or lacks memory gives its reason and the
  next one is tried.
- `gpu_for(use_gpu, purpose=...)`: `False` the CPU; `None` ("auto") a usable GPU, else the CPU
  with a `GPUFallbackWarning`; `True` ("required") a usable GPU, else `NoUsableGPUError`.
  Messages as the parked MATLAB change: "No GPU is available (1 found,
  CUDA_VISIBLE_DEVICES='5'), so the deconvolution runs on the CPU. <reason>".

### 5. Memory between tasks (`petakit5d.gpu.memory`)

Inside a task CuPy's pool reuses memory. After each task (`task_scope`) the pool's cached blocks
go back to the GPU (the next task's free-memory check is then true, and other processes on a
shared GPU get the memory back); the CUDA context and the cached FFT plans stay (`keep_plans`).
`track_peak` gives the peak pool use (FFT work areas included; the context and cuFFT's internal
buffers, 8 to 10 MiB per plan, not).

- The cached GPU start (import, context, first plan) is 0.4 to 0.6 s for a whole process on
  Titan V, V100 and A100 and 1.45 s on B200: the 3 s target is met on all of them.
- On the B200 nodes CUDA's initialization (`cuInit`, in "count GPUs") alone takes 0.81 to 0.84 s;
  their GPUs have persistence mode disabled, the likely cause (0.05 s on the Titan V nodes).
- cuFFT 11.0.8 on B200: the driver compiles its PTX at the first plan and transform of a size
  (about 0.1 s each); the FFT speed equals 11.4.1 (demo tile R2C + C2R: Titan V 0.063 s,
  A100 0.0198 s, B200 0.0058 s with either version).
- A first plan of a new size costs about 0.15 s more when the **driver's** JIT cache
  (`CUDA_CACHE_PATH`, default `~/.nv/ComputeCache`) doesn't have it; our kernel cache and CuPy's
  don't affect it. Clusters that wipe home caches pay it once per job and size.
- A cache on network storage instead of local disk: no measurable difference (0.54 s).
- Importing the four modules (device, kernels, fft, memory) costs 19 ms (bytecode, local disk;
  11 ms of it `petakit5d.gpu.device`), and neither CuPy nor NumPy.
- The demo tile's work area: 1.76 GiB for both plans (both cuFFT versions), the size of a half
  spectrum; small sizes need none in cuFFT 11.4 and 32 MiB in 11.0.8.

### cuFFT against MATLAB on the same GPU

MATLAB R2024b (its bundled cuFFT is 11.0.8.103); random single inputs of 7 sizes (64^3,
128 x 96 x 80, 127 x 61 x 33, 100 x 100, 256 x 256 x 128, 181 x 512 x 101, 1800 x 512 x 50).
"Identical" is bit for bit; otherwise the share of differing values and the largest difference
relative to the largest magnitude.

| Comparison (Titan V) | cuFFT 11.0.8 (as MATLAB) | cuFFT 11.4.1 (default) |
|---|---|---|
| our R2C vs the GPU mex's half OTF (`decon_lucy_rfft_gpu_mex('otf')`) | identical, 7 of 7 | identical 1 of 7; else 34-90%, at most 5e-8 |
| our C2R / N vs `ifftn(F, 'symmetric')` | identical 6 of 7 (181 x 512 x 101: 87%, 9e-7) | identical 1 of 7; else 38-88%, at most 1e-6 |
| our R2C vs gpuArray `fftn` (its first half) | 86-94%, at most 2e-7 | the same |
| our C2C of `complex(x)` vs gpuArray `fftn(x)` | identical, 3 of 3 | identical 1 of 3; else 40-72%, at most 1.4e-9 |
| our C2C inverse / N (each part divided) vs `ifftn(F)` | identical, 3 of 3 | identical 1 of 3; else 41-71%, at most 4.8e-7 |

| Comparison (A100 and B200, each, 7 sizes) | cuFFT 11.0.8 | cuFFT 11.4.1 |
|---|---|---|
| R2C vs the mex's half OTF | identical, 7 of 7 | identical 1 of 7; else 34-90%, at most 5e-8 |
| C2C of `complex(x)` vs `fftn(x)` | identical, 7 of 7 | identical 1 of 7; else 40-88%, at most 1.1e-7 |
| C2C inverse / N vs `ifftn(F)` | identical, 7 of 7 | identical 1 of 7; else 41-87%, at most 7.2e-7 |
| C2R / N vs `ifftn(F, 'symmetric')` | identical 6 of 7 (181 x 512 x 101 as on Titan V) | identical 1 of 7; else 38-88%, at most 1e-6 |

On the B200, MATLAB ran with forward compatibility (its libraries compiled by the driver; the
whole MATLAB process 12.8 s with an empty CUDA cache) and our cuFFT 11.0.8 from driver-compiled
PTX: the bits agree as on the GPUs both support natively.

- Our R2C plans are the mex's plans: with the cuFFT version MATLAB bundles, the GPU decon
  kernels (K09) can match the mex bit for bit.
- MATLAB's gpuArray `fftn` of real data is a 3D complex-to-complex transform of `complex(x)`
  (its full spectrum is not exactly conjugate-symmetric), and `ifftn` the complex inverse
  divided by N: `ComplexFFTPlan` reproduces both bit for bit with cuFFT 11.0.8. MATLAB's default
  GPU decon path uses them (the mex is not the GPU default), so R04 can match it exactly with
  full spectra, or use half spectra (less memory) within a tolerance: a choice for the user.
- Dividing by N is not multiplying by 1/N (11% of values differ at 127 x 61 x 33); CuPy's
  `complex64 / float32` gives the latter, so the scaling must be our componentwise division.
  MATLAB divides in double and rounds to single (`single ./ double`): the same bits as a
  division in single while N is a single, but at 181 x 1031 x 101 (N = 18,847,711, not a
  single) only the division in double gives MATLAB's bits (a division by `single(N)` changes 65%
  of the values), on all three GPUs.
- The same input gives the same bits from run to run on one GPU.

B200, with the same results on the three:

| Comparison (MATLAB sizes) | Result |
|---|---|
| `MatlabFFTPlan.forward` of the volume vs gpuArray `fftn(x)` | identical, 8 of 8 |
| `MatlabFFTPlan.inverse` vs `ifftn(F)` | identical, 8 of 8 |
| `RealFFTPlan(matlab_shape)` on `matlab_order(vol)` vs the mex's half OTF | identical, 8 of 8 |
| its C2R / N vs `ifftn(F, 'symmetric')` | identical 6 of 8 (181 x 512 x 101 and 181 x 1031 x 101: 87-91%, 8e-7, as before) |

| native C2C inverse / N vs `ifftn(F)` | 87-95%, at most 1.1e-6 |

- In the GPU tests `MatlabFFTPlan` equals the plan in MATLAB's layout (`ComplexFFTPlan` of
  `matlab_shape` on `matlab_order(vol)`) bit for bit, also with size-1 axes, images and odd sizes,
  and has its work area: the C2C plans need none (8 bytes) at 128 x 256 x 256 and at the demo
  tile (500 x 1800 x 512), where the native R2C pair needs 32 MiB and 1.72 GiB. A full spectrum
  without a work area takes the GPU memory of a half spectrum with its work area (8 bytes per
  voxel).
- The native plans round differently (the forward transform within about 1 ulp of the largest
  value): their differences enter the GPU tolerance of a step that uses them (half spectra, R04's
  option).
- Steady state, ms per forward and inverse transform (the demo tile; Titan V: 200 z planes):

| GPU | native R2C + C2R (half) | `MatlabFFTPlan` forward + real inverse | MATLAB's plan on MATLAB's layout, with CuPy's casts | its C2C pair alone | one transpose |
|---|---|---|---|---|---|
| Titan V | 20.6 | 48.0 | 47.8 | 40.3 | 5.0 |
| A100 | 19.8 | 38.1 | 38.1 | 30.9 | 4.5 |
| B200 | 7.8 | 11.1 | 12.8 | 9.2 | 1.1 |

- The transposes cost what the casts around a C2C transform of real data cost: `MatlabFFTPlan` on
  (z, y, x) volumes is as fast as MATLAB's plan on data already in MATLAB's layout (13% faster on
  the B200). Full spectra take 1.4 (B200) to 2.3 (Titan V) times the half spectra's time.
- Start-up, cached: each step as before (import CuPy 0.13-0.20 s, count GPUs 0.05-0.74 s, context
  0.10-0.15 s, first native plan 0.004-0.005 s); the MATLAB plan after it adds 0.001-0.002 s (its
  kernels from our cache). First use adds 0.10-0.30 s: NVRTC compiles the layout kernels
  (0.07-0.14 s), and the plan's first use.
- Rejected on the way: 1D transforms in MATLAB's order (z, x, then y) on the (z, y, x) layout give
  MATLAB's bits at some sizes only.

### cuFFT 11.4.1 (and the CUDA 13 line) against 11.0.8

Decided: cuFFT 11.0.8.103 is the pin. The newer versions were measured on A100 and B200 (10 sizes:
powers of two, 5-smooth, prime, the decon and registration sizes; single and double; C2C, R2C and
C2R), against a double reference for single and a long double reference for double:

- **Not less accurate, differently rounded.** Single precision relative L2 error of 11.4.1 equal
  to or up to 20% below 11.0.8's (decon slab 1800 x 512 x 64: 1.9e-7 against 2.4e-7); double
  precision equal to NumPy's double FFT (1 to 5e-16) for every version. 11.4.1 differs from
  11.0.8 in 38-86% of values, mostly by 1 or 2 ulps (99% within 4 ulps, all within 10 ulps of
  the largest value).
- **No faster.** Steady state equal within 1% on both GPUs (demo tile R2C + C2R: B200 12.3 ms,
  A100 63.7 ms with either). On the B200, 11.0.8's first use of a size with an empty driver cache
  costs up to 0.15 s more (PTX compiled by the driver).
- **End to end** (Richardson-Lucy, MATLAB's GPU steps, 30 iterations, a demo tile): 11.4.1
  changes 0.0019% of the uint16 voxels, each by 1 (relative L2 2.8e-6 in single).
- Every version is deterministic, run to run and process to process. cuFFT 12.0 (CUDA 13.0) gives
  11.4.1's bits; 12.5 (CUDA 13.5) gives them on the A100 but not on the B200, where two power of
  two sizes are about 3 times less accurate. None returns to 11.0.8's bits.
- If a newer cuFFT is ever needed, a tolerance of 1 count in at most 0.01% of uint16 voxels (and
  relative L2 1e-5 for single outputs) covers it with a fivefold margin.

### Compilers and targets

The same kernels (multiply-add without contraction, division, square root, floor, `expf`,
`logf`, `sinf`, a double computation) compiled by NVRTC 12.9 and 12.2, as cubins and as PTX the
driver compiled: bit-identical on Titan V and A100, and on the B200 the `sm_100` cubin of
NVRTC 12.9 equals the `compute_90` PTX of NVRTC 12.2 (which doesn't know the GPU), the
`compute_100` PTX of NVRTC 12.9 and the cubin of NVRTC 13.5, in every output. The foundation's
74 tests pass on the B200 with each compiler.

## Consequences for the GPU ports

- Kernels follow `cpp/cuda/README.md`: device code only (no host headers), `float2` for complex,
  `extern "C"` names or name expressions.
- **CuPy element-wise operations flush subnormals** (`-ftz=true`), may contract `a * b + c`
  into fused multiply-adds, and divide a complex array by a real scalar as a multiplication by
  its reciprocal: glue code whose bits must match MATLAB (scaling, offsets, conversion before
  uint16) belongs in our kernels, or must be shown not to meet those cases.
- With cuFFT 11.0.8.103 (MATLAB's version, the pin) GPU FFTs equal MATLAB's on the same GPU
  model; with 11.4.1 they differ in the last bits, and those differences would be measured and
  proposed as tolerances per output.
- A step that must give MATLAB's bits (R04's default) uses `MatlabFFTPlan` and keeps its spectra
  (OTFs too) in MATLAB's layout; one that uses the native plans (half spectra) takes their
  measured differences into its tolerance.
- GPU memory per voxel can be planned from `work_bytes` (the shared area of `RealFFTPlan`; none
  for `MatlabFFTPlan`, whose spectrum takes 8 bytes per voxel).

## Alternatives considered

- **Kernels compiled at build time (nvcc fatbins)**: needs a toolkit in every build, fixes the
  architectures at build time (a GPU newer than the build needs PTX anyway), and makes wheels
  large. Rejected.
- **CuPy `RawModule` and its cache**: see 2.
- **`cupy.fft` / `cupyx.scipy.fft`**: one work area per plan, no control over plan dimensions;
  differs from the mex's plans. Kept for glue that doesn't feed outputs.
- **MATLAB's bits on the (z, y, x) layout without a scratch in MATLAB's layout**: no cuFFT plan
  over (z, y, x) memory has MATLAB's dimensions, and 1D transforms in MATLAB's order give its
  bits at some sizes only. The spectra stay in MATLAB's layout instead (`MatlabFFTPlan`).
- **CUDA 13 wheels**: drop Volta (Titan V, V100), and their NVRTC can be newer than the driver
  (PTX then fails). Revisit when no such GPU is in use.
- **NVML for free memory without a context**: would list other processes on the GPU, but adds a
  library; the context's `cudaMemGetInfo` gives what matters (memory this process can get).
